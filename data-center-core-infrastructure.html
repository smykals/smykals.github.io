Keeping Campus Network Cores Powered and Reachable

Building, auditing and restoring the core racks every user on a campus network depends on: redundant power, a way in when the network is down, and the equipment in between.

Environment
University data center rooms, network closets and a shared colocation
Scale
1,000+ access points and 250 switches across my assigned sites
My roles
Network Specialist; Regional Field Supervisor from 2020
Scope
Network equipment, cabinet power and console access, not building power or cooling

The Challenge

Each campus sent every user through a single core rack. If that rack lost power, or a key device in it failed, the whole campus could lose its internet connection. At a colocation that served several schools at once, one fault could affect all of them.

The work was keeping those cores redundant, reachable even when the main network was down, and documented well enough that anyone on the team could work on them safely.

How a Core Fits Together

  1. Internet circuitDirect to the campus, or a transport link to a colocation
  2. →
  3. Border routingNAT and the edge of the network
  4. →
  5. Core switchRouting between VLANs and access control
  6. →
  7. Core servicesWireless controllers, DHCP and user authentication
  8. →
  9. CampusMDFs, IDFs, access switches and access points

At transport sites, DHCP, authentication and DNS lived at the colocation instead of on campus, so troubleshooting had to account for both ends.

Two Paths That Keep a Core Alive

  1. Separate power feedsTwo UPSs, ideally on separate circuits
  2. →
  3. Two PDUsEach plugged into a different UPS
  4. →
  5. Dual power suppliesEvery core device fed from both PDUs
  1. Cellular routerIndependent of the campus internet circuit
  2. →
  3. Console serverOne port per core device
  4. →
  5. Console portsDirect access to each device, even with the network down

Redundant power keeps a core running through a failed UPS, PDU, outlet or circuit. Out-of-band access means a failed core can still be reached and diagnosed.

How an Outage Was Handled

  1. DispatchPriority set by scope; full core outages meant hours, not days
  2. →
  3. IsolateOut-of-band check: provider fault or our own core?
  4. →
  5. EscalateSymptoms, scope, timing and device details to engineering
  6. →
  7. RestoreHands-on fix, inside change control even under pressure
  8. →
  9. Close outRoot cause recorded and documentation updated

A generalized flow. Who owned each step depended on the cause: outages caused by building power or the internet provider were handled differently from faults in our own equipment.

What I Did

  • Built Out-of-Band Access

    Configured and installed a cellular router and a console server in core racks, cabled every core device's console port (using RJ45-to-DB9 adapters where a device needed one), and documented which console port went to which device so engineering could reach any of them.

  • Verified Redundant Power

    Checked that core equipment drew power from two PDUs fed by separate UPSs, corrected cabling where it didn't, and kept each site's UPS-to-PDU power documentation current.

  • Brought Power and Console Devices Under Monitoring

    Replaced default logins on UPSs, PDUs and console servers, configured SNMP so monitoring read real device data rather than just up or down, labeled outlets and console ports by device, and confirmed each node appeared in monitoring.

  • Tested and Replaced UPS Batteries

    Read UPS status and alerts, compared expected runtime between paired units to spot a failing battery, ran self-tests and runtime calibrations, and replaced failed batteries.

  • Audited Sites and Cores Against Standards

    Checked switches against configuration standards, including naming, SSH, ISE, firmware, NTP and SNMP, DHCP snooping, spanning-tree root placement, optic light levels and interface errors, and opened work orders for anything that didn't match.

  • Responded to Priority Dispatches

    Answered core and campus-wide outage dispatches on site, including after hours, within response targets set by how many users were affected.

  • Used Out-of-Band Access to Isolate Faults

    When a campus lost connectivity, came in through the cellular path to check the core directly, which separated an internet-provider fault from a problem in our own equipment.

  • Escalated With Evidence

    Before handing an issue to engineering, gathered the exact symptoms, scope, when it started, environmental factors such as power or weather, and the affected devices, so engineering could start immediately.

  • Led On Site During Outages

    Served as the on-site contact during outages, including building power outages where field services owned the status updates until power returned.

  • Worked Within Change Control

    Did planned work inside approved maintenance windows with advance notice, a written method of procedure and a rollback plan.

  • Supported Both Core Designs

    Worked on direct-internet cores with every service on campus, and on transport sites that depended on a colocation for DHCP, authentication and DNS.

  • Worked Hands-On Across the Core

    Core and border switches, NAT border routers, wireless controllers, and DHCP and authentication servers: hardware swaps, optics and cabling, chassis-part inventory, and careful one-at-a-time restarts of paired servers when engineering approved them.

  • Worked in a Shared Colocation

    Performed rack work in a colocation serving many schools at once, where every change affected more than one campus and had to be deliberate.

  • Trained Technicians on the Standards

    As a supervisor, trained and coached field technicians on these audits, procedures and standards, so the same checks happened the same way at every site.
