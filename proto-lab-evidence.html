01 / Personal-lab incident / Application access verified

Inter-zone Proxmox GUI failure

Environment: FortiGate, managed switching, Proxmox VE, and a segmented OT learning lab.

Problem
A trusted management endpoint could reach the virtualization host at the network layer, but could not open the Proxmox web interface.
My investigation
I confirmed that pveproxy was listening on TCP/8006 and examined firewall flow debugging. The firewall received the connection and found a route to the OT zone, but rejected the session at the forward-policy check.
Sanitized transcript excerpt
received packet: TCP [management endpoint]:[ephemeral] -> [OT virtualization host]:8006
find a route: destination reachable via OT zone
Denied by forward policy check (policy 0)
Destination service check: *:8006 LISTEN pveproxy
Reasoning
A listening service and an available route narrowed the failure domain to policy enforcement. The flow trace identified where the connection stopped.
Root cause and my change
The administrative path lacked an explicit inter-zone permit policy. I added a narrowly scoped rule for the required management traffic, with internal NAT disabled.
Verification
The Proxmox GUI became reachable from the authorized management path after the change. This checked application access rather than relying only on ICMP.
Result context
This validates the tested administrative path. It does not establish that all segmentation policies or OT process integrations have been tested.
02 / Personal-lab incident / DNS filtering verified

VPN DNS filtering bypass

Environment: Ubuntu VPN host, WireGuard, AdGuard Home, Unbound, and a Windows client.

Problem
The VPN tunnel worked, but DNS-based filtering was not being applied to the remote client.
My investigation
I captured DNS traffic on the VPN interface. Queries were traversing the tunnel, but were addressed to a different resolver instead of the filtering DNS service.
Sanitized transcript excerpt
$ sudo tcpdump -ni wg0 'host [VPN client] and port 53'
Client connected? YES
VPN passing DNS? YES
DNS queries present? YES
Going to AdGuard? NO
Observed destination: external resolver
Expected destination: VPN filtering DNS service
Reasoning
The capture separated tunnel transport from resolver selection. DNS traffic existed on the tunnel, so the investigation focused on where the queries were sent.
Root cause and my change
The client DNS setting pointed to the wrong resolver. I changed the VPN client configuration to use AdGuard Home on the VPN host.
Verification
Subsequent queries appeared in AdGuard Home. The query log and blocked-domain results confirmed filtering for the tested queries.
Result context
This confirms the tested DNS path and filtering behavior; it is not a claim that all clients or alternate DNS methods were assessed.
03 / Personal-lab implementation / Remote session verified

Remote administrative access path

Environment: Dedicated Linux VPN host, Tailscale, a Windows jump-host VM, and Proxmox VE.

Objective and my implementation
I established a private remote-administration path through the VPN boundary and Windows jump host, avoiding direct public exposure of hypervisor and management interfaces.
Sanitized logical path
Remote trusted endpoint
  → Private overlay VPN
  → Dedicated VPN host
  → Windows jump host (RDP)
  → Authorized management resources

Separate recovery path:
VPN → Hypervisor console → Jump-host console
Verification
I configured Remote Desktop on the Windows host, confirmed TCP/3389 was listening, and successfully established a remote session through the private access path.
Result context
The record validates an RDP session through the administrative path. The separate recovery route is documented as an architectural path; a completed recovery drill is not recorded.
04 / Personal-lab investigation / Capacity decision

Virtualization capacity investigation

Environment: Proxmox VE with Windows 11 and Linux guests on a memory-constrained host.

Problem
The Windows jump-host VM showed high memory utilization while sharing a host with other workloads.
Evidence
The VM summary recorded 99.92% memory utilization with 6.00 GiB assigned. A later host view showed approximately 89.5% host memory utilization while Windows and Linux guests were present.
My analysis and design decision
I reviewed guest allocation and ballooning against total host capacity. Increasing guest allocation could move the bottleneck to the host, so I treated host memory as the limiting resource and considered headroom for the hypervisor and other workloads.
Result context
The evidence supports a capacity investigation and design decision. No final allocation, post-change utilization, performance improvement, or long-term stability result is recorded.

What this demonstrates

Separate service availability, routing, policy, and application behavior. Make the smallest justified change, then verify at the layer where the original problem occurred.
